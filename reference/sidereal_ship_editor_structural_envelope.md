# Sidereal Ship Editor — Structural Envelope & Wall System

## Status

Working design document for the **Sidereal Ship Layout Planner**.

This document defines how the editor should handle:

- Floor tiles / floor polygons
- Automatically generated exterior boundaries
- Interior walls placed on grid lines
- Angled and clipped ship shapes
- Cockpits and fronts that do not use conventional vertical walls
- Windows, ramps, airlocks, hangar doors, engine mounts, and other edge treatments
- Exterior hull skin and armour
- Pressure sealing and validation
- Multi-deck compatibility
- Faction/theme-specific ship appearances

The key architectural principle is:

> **Floor generates boundaries. Boundaries do not necessarily generate walls.**

A wall is only one possible way to satisfy an exterior or interior boundary.

---

# 1. Problem

The first version of the ship editor treats the edge of the floorplan approximately like this:

```text
floor ends here
      ↓
spawn wall
```

This works for simple rectangular rooms, but it quickly causes problems for spacecraft.

A ship exterior may contain:

- Angled armour
- Sloped noses
- Cockpit glass
- Low hull sections
- Windows
- Ramps
- Hangar openings
- Airlocks
- Thruster mounts
- Engine interfaces
- Exterior platforms
- Open construction edges
- Curved or stepped hull treatments

For example, a cockpit may have a perfectly valid pressure boundary without having a normal 3 m vertical wall.

The system therefore needs to distinguish between:

1. **Walkable floor**
2. **Structural boundary**
3. **Boundary treatment**
4. **Exterior hull skin**
5. **Armour / decorative modules**

These are related, but they are not the same thing.

---

# 2. Recommended Layer Model

Use the following logical hierarchy:

```text
Floor
  ↓
Structural Boundary
  ↓
Boundary Treatment
  ↓
Hull Skin
  ↓
Armour / Exterior Detail
```

A more visual representation:

```text
                   EXTERIOR SHELL / ARMOUR
              ┌─────────────────────────────┐
             /                               \
            /   windows / canopy / armour    \
           /                                   \
          ├───── STRUCTURAL ENVELOPE EDGES ─────┤
          │                                      │
          │  room  │ corridor │      room        │
          │        │          │                  │
          │────────┼──────────┼──────────────────│
          │                                      │
          └────────── WALKABLE FLOOR ────────────┘
```

The floor determines topology.

The structural boundary determines where the ship interior stops.

The boundary treatment determines what is physically present at that location.

The hull skin determines how the ship looks externally.

# 3. Floor System

The designer places floor shapes on the construction grid.

Supported floor primitives may include:

- Rectangle
- Square
- Right triangle
- Isosceles triangle
- Clipped corner
- Trapezoid
- Narrow wedge
- Custom polygon
- Area fill
- Line fill

Floor pieces should ultimately resolve into polygons aligned to the editor construction grid.

Example:

```text
        ████
      ████████
    ████████████
    ████████████
      ████████
```

The editor calculates the union of all connected floor polygons.

The perimeter of this union becomes the **exterior structural boundary**.

---

# 4. Structural Boundary Graph

Do not store walls directly on tiles using fields such as:

```ts
tile.northWall
tile.southWall
tile.eastWall
tile.westWall
```

That approach becomes difficult once the editor supports:

- Diagonal edges
- Triangles
- Trapezoids
- Clipped corners
- Arbitrary polygons
- Non-orthogonal hulls

Instead, represent the floorplan using vertices and edges.

Example:

```ts
interface GridVertex {
    id: string;
    x: number;
    y: number;
}

interface FloorPolygon {
    id: string;
    vertices: GridVertex[];
}
```

Each polygon produces edges between consecutive vertices.

An edge can be represented as:

```ts
interface StructuralEdge {
    id: string;

    a: GridVertex;
    b: GridVertex;

    kind:
        | "exterior"
        | "partition";

    treatment: BoundaryTreatmentType;

    sealed: boolean;
    collision: boolean;
    blocksVision: boolean;

    profile?: string;
    style?: string;
}
```

---

# 5. Edge Canonicalisation

Edges must be canonicalised so that:

```text
A → B
```

and:

```text
B → A
```

are recognised as the same structural edge.

For example:

```text
Polygon A owns edge 10 → 11
Polygon B owns edge 11 → 10
```

These should resolve to one shared edge.

A simple canonical edge key can be generated by sorting vertex IDs:

```ts
function edgeKey(a: GridVertex, b: GridVertex): string {
    return a.id < b.id
        ? `${a.id}:${b.id}`
        : `${b.id}:${a.id}`;
}
```

Edge ownership then determines its structural meaning.

### One floor owner

```text
EXTERIOR BOUNDARY
```

### Two floor owners

```text
INTERNAL SHARED EDGE
```

### Zero owners

```text
NO STRUCTURAL EDGE
```

# 6. Exterior Boundary Generation

Floor placement should automatically generate exterior boundary edges.

Example floor:

```text
        ┌────┐
      ╱        ╲
    ╱            ╲
    │            │
    │            │
      ╲        ╱
        └────┘
```

The perimeter should initially receive:

```text
AUTO
AUTO
AUTO
AUTO
...
```

The designer should not need to manually draw every exterior edge.

The default edge treatment is:

```ts
treatment = "auto";
```

The active ship hull/theme resolves `auto` into an appropriate structural treatment.

For example:

```text
Wayfarer Industrial Hull
AUTO → Reinforced Hull Wall A
```

while another faction might resolve the same edge into:

```text
Alien Organic Hull
AUTO → Ribbed Chitin Shell B
```

---

# 7. Boundary Treatments

Exterior edges should support multiple treatments.

Recommended initial set:

```ts
type BoundaryTreatmentType =
    | "auto"
    | "vertical-hull"
    | "sloped-hull"
    | "low-hull"
    | "cockpit-glass"
    | "window"
    | "bulkhead"
    | "airlock"
    | "door"
    | "ramp"
    | "hangar-door"
    | "engine-interface"
    | "docking-interface"
    | "open-bay"
    | "open"
    | "custom";
```

These treatments determine what geometry is generated for the edge.

# 8. The Cockpit Problem

A cockpit does **not** have no wall.

It has no conventional vertical wall.

Consider the front of a ship:

```text
             /────────────\
           /                \
         /                    \
        |      BRIDGE          |
        |                      |
        └──────────────────────┘
```

The front edges are still:

```ts
exteriorBoundary = true
pressureBoundary = true
collisionBoundary = true
```

But their treatment may be:

```text
CockpitGlass
SlopedHull
LowHull
```

instead of:

```text
VerticalHull
```

Example generated geometry:

```text
             upper canopy frame
                  ↓
             ╱════════╲
          ╱              ╲
       ╱    windshield     ╲
    ╱                         ╲
 ═╯___________________________╰═
 ↑             ↑
low hull     cockpit floor
```

The floor boundary remains valid.

Only the generated boundary mesh changes.

Each edge treatment should define both visual and gameplay properties.

Example:

```ts
interface BoundaryTreatmentDefinition {
    id: string;

        | "glass"
        | "opening"
        | "door"
        | "interface"
        | "special";

    collision: boolean;
    blocksVision: boolean;
    blocksProjectiles: boolean;

    supportsPressure: boolean;

    meshProfile?: string;
```

Example cockpit glass:

```ts
{
    id: "cockpit-glass",
    category: "glass",

    sealed: true,
    collision: true,
    blocksVision: false,
    blocksProjectiles: true,

    supportsPressure: true

```

Example open construction edge:

```ts
{
    id: "open",
    category: "opening",

    sealed: false,
    collision: false,
    blocksVision: false,
    blocksProjectiles: false,

    supportsPressure: false
}
```

# 10. Interior Walls

Interior walls should be placed on **edges between floor regions**, not inside floor cells.

Example:

```text
+---+---+---+---+
|   |   |   |   |
+   +---+   +   +
|       |       |
+---+---+---+---+
```

The cells represent walkable floor.

The lines represent structural partitions.

Interior walls can therefore use the same edge graph used by exterior boundaries.

The difference is:

```ts
kind = "partition";
```

rather than:

```ts
kind = "exterior";
```

---

# 11. Interior Wall Placement

The editor should provide a dedicated partition-wall tool.

The user selects two grid vertices or drags along valid grid edges.

Example:

```text
floor floor floor floor
  │
  │ interior wall
  │
floor floor floor floor
```

A partition should exist independently of the floor tile geometry.

This makes it possible to:

- Split one large floor area into rooms
- Move walls without replacing flooring
- Detect enclosed rooms
- Add doors directly to wall segments
- Use diagonal partitions
- Use faction-specific internal wall styles

---

# 12. Doors and Openings

Doors should not occupy a complete floor tile.

They should attach to an existing structural edge.

Conceptually:

```text
Normal wall:

───────────────

Wall with door:

────── [ ] ──────
```

An opening can either:

1. Replace an entire structural segment, or
2. Occupy a sub-range of a longer structural segment

A useful model is:

```ts
interface EdgeOpening {
    id: string;
    edgeId: string;

    type:
        | "door"
        | "window"
        | "airlock"
        | "hatch"
        | "service-opening";

    offset: number;
    width: number;
}
```

This becomes useful once walls are longer than one grid unit.

---

# 13. Room Detection

Because walls and exterior boundaries exist as an edge graph, the editor can perform room detection.

A room is a connected floor region enclosed by:

- Exterior structural edges
- Interior partition edges
- Closed doors / pressure doors where appropriate

This can support:

- Automatic room selection
- Room naming
- Atmosphere simulation
- Pressure zones
- Fire zones
- Navigation
- Lighting groups
- Oxygen systems
- Power systems
- AI behaviour

Example:

```text
┌───────────────┬─────────────┐
│               │             │
│    CREW       │   MEDBAY    │
│               │             │
├───────────────┴──────┬──────┤
│                      │      │
│      CORRIDOR        │STORE │
│                      │      │
└──────────────────────┴──────┘
```

These spaces can be detected from the wall topology instead of being manually painted.

# 14. Exterior Hull Skin

The **structural boundary** should not necessarily be the visible outer surface of the ship.

The visible hull should be generated as a separate layer.

Structural boundary:

```text
        ┌──────────────┐
        │              │
────────┘              └────────
```

Exterior hull skin:

```text
           armour
         ╱▀▀▀▀▀▀▀▀▀▀╲
       ╱              ╲
     ╱  ┌──────────┐   ╲
────╯   │ interior │    ╰────
        └──────────┘
```

This separation allows:

- Armour thickness
- External bracing
- Decorative recesses
- Radiators
- Vents
- Lighting strips
- Faction-specific hull silhouettes
- Raised plating
- Greebles
- External engine housings

without changing the actual walkable area.

The hull generator consumes the exterior boundary graph.

Input:

```text

```

Output:

```text
Exterior hull strips

Canopy assemblies
Engine mounting geometry
Armour modules
```

Conceptually:

```text
Floor
  ↓
Structural Boundary
  ↓
```

A hull profile might define:

```ts
interface HullProfile {
```

# 16. Hull Theme / Faction System

The same floorplan should be able to produce different exterior appearances.

Example:

```text

        ├── Corporate Clean
        ├── Pirate Scrap
        ├── Military Heavy
        └── Alien Organic
```

Only the hull theme changes.

# 17. Engine Interfaces

Engines are a strong reason not to treat every exterior boundary as a wall.

A rear edge may instead be:

```text
ENGINE INTERFACE
```

Example:

```text
 interior
    │
    │
════╪════════ structural envelope
    │
    ├══ reactor plumbing
    ├══ electrical
    ├══ coolant
    │
 [ ENGINE ]
       ╲
        ╲ exhaust
```

The edge can still be pressure sealed while allowing an engine module to attach outside the ship.

Example validation rule:

```text
Thruster modules may only attach to:
- engine-interface
- custom engine mount
```

This creates a useful relationship between:

- Structure
- Hull
- Engines
- Systems
- Piping
- Wiring

# 19. Open Exterior Edges

The editor should allow a temporary or intentional `open` boundary state.

Example:

```ts
{
    treatment: "open",
    sealed: false
}
```

This is useful during construction.

The editor should permit it but produce validation warnings.

Example:

```text
⚠ Deck A has 4 unsealed exterior boundary segments.
```

Do not block editing simply because the ship is temporarily invalid.

This allows workflows such as:

1. Draw cargo bay
2. Leave rear open
3. Add ramp
4. Add airlock
5. Seal hull
6. Validation becomes clean

# 20. Ramps and Hangar Doors

A ramp or hangar door should behave as an exterior boundary treatment.

Example:

```text
Closed:

██████████████
   HANGAR
██████████████


Open:

████          ████
      OPEN
     HANGAR
```

The structural edge remains the same.

Only its state changes.

Example runtime properties:

```ts
sealed = door.closed;
collision = door.closed;
blocksVision = door.closed;
```

This same system can support:

- Cargo ramps
- Personnel ramps
- Docking clamps
- Blast doors
- Vehicle bay doors
- Airlocks

# 25. Geometry Generation Pipeline

Recommended pipeline:

```text
Placed Floor Shapes
        ↓
Polygon Normalisation
        ↓
Floor Union
        ↓
Edge Extraction
        ↓
Edge Canonicalisation
        ↓
Boundary Classification
        ↓
Structural Boundary Graph
        ↓
Boundary Treatments
        ↓
Interior Wall Generator
        ↓
Exterior Hull Generator
        ↓
Armour / Detail Generator
        ↓
Validation
```

# 26. Boundary Classification Algorithm

Pseudo-code:

```ts
const edges = new Map<string, EdgeOwnership>();

for (const polygon of floorPolygons) {
    for (const edge of polygonEdges(polygon)) {
        const key = canonicalEdgeKey(edge.a, edge.b);

        let record = edges.get(key);

        if (!record) {
            record = {
                a: edge.a,
                b: edge.b,
                owners: []
            };

            edges.set(key, record);
        }

        record.owners.push(polygon.id);
    }
}

for (const edge of edges.values()) {
    if (edge.owners.length === 1) {
        createExteriorBoundary(edge);
    }

    if (edge.owners.length === 2) {
        createInternalSharedEdge(edge);
    }
}
```

For overlapping or more complicated polygons, first normalise the floor geometry so edge extraction occurs against the resolved polygon union rather than raw overlapping stamps.

# 27. Supporting Arbitrary Angles

The structural system should not assume four cardinal directions.

Instead, an edge has:

```ts
a: Vec2;
b: Vec2;
```

From this we can derive:

```ts
direction = normalize(b - a);
normal = perpendicular(direction);
length = distance(a, b);
```

This allows:

- 90° walls
- 45° walls
- Narrow wedges
- Clipped corners
- Arbitrary hull profiles

The grid can still constrain the allowed vertices if desired.

---

# 28. Grid Design

The editor may use a 1 m main construction grid while exposing smaller hull/detail subdivisions.

Possible structure:

```text
Primary floor grid:
1.0 m

Structural vertex subdivision:
0.5 m

Hull detail sockets:
0.25 m
```

This allows structural layouts to remain simple while giving exterior pieces more fidelity.

Floor cells should not need to become extremely small just to create detailed armour geometry.

---

# 29. Corner Handling

Exterior hull generation needs explicit handling for:

- Straight edge
- Convex corner
- Concave corner
- Acute corner
- Obtuse corner
- Transition between boundary treatment types

Examples:

```text
Convex:

─────╲
      ╲


Concave:

─────┐
     │
```

The hull theme should provide suitable corner pieces or procedural corner geometry.

The system should not simply overlap two wall meshes.

---

# 30. Boundary Segmentation

Long edges should be internally segmented according to useful construction units.

For example:

```text
12 m edge
```

might be represented as:

```text
[2m][2m][2m][2m][2m][2m]
```

This allows:

- Windows
- Doors
- Armour sections
- Damage sections
- Hull variants
- Detail modules

without requiring the entire edge to become one giant mesh.

Logical topology can still retain the complete edge relationship.

---

# 31. Exterior Hull Offsets

Hull geometry should usually extend outward from the structural boundary.

Example:

```text
INTERIOR

──────────── structural boundary
████████████ hull thickness
▒▒▒▒▒▒▒▒▒▒▒ armour
```

This ensures armour and wall thickness do not consume the interior floor area.

Recommended fields:

```ts
interface HullGeometrySettings {
    structuralThickness: number;
    exteriorOffset: number;
    armourOffset: number;
}
```

---

# 32. Multiple Decks

Each deck should have its own floor union and boundary graph.

Example:

```text
Deck C
    ↓
Deck B
    ↓
Deck A
```

Deck footprints do not need to match.

This enables:

```text
        Deck C
       ┌──────┐

      Deck B
    ┌──────────┐

     Deck A
  ┌──────────────┐
```

The exterior hull system can then create sloped transitions between footprints.

---

# 33. Vertical Structural Relationships

A future multi-deck model may use:

```ts
interface Deck {
    id: string;
    elevation: number;
    height: number;

    floorPolygons: FloorPolygon[];
    boundaryGraph: StructuralGraph;
}
```

The hull generator can compare adjacent decks.

For example:

```text
Deck B edge lies 2 m inward from Deck A
```

can produce:

```text
sloped armour transition
```

instead of a vertical wall.

This will be important for making ships look like actual spacecraft rather than stacked boxes.

# 34. Exterior Envelope Generation Across Decks

Eventually the hull generator should operate on the full 3D structural envelope.

Conceptually:

```text
Deck A floor polygon
        +
Deck B floor polygon
        +
Deck C floor polygon
        ↓
3D structural envelope
        ↓
Hull skin
```

This allows:

- Tapered noses
- Raised bridges
- Recessed engineering decks
- Multi-storey hangars
- Stepped armour
- Observation decks
- Engine towers

# 35. Collision

Collision should be derived from structural treatments rather than visual hull meshes alone.

Examples:

## Normal hull

```text
collision = true
```

## Cockpit glass

```text
collision = true
```

## Open bay

```text
collision = false
```

## Low hull

```text
collision = true
```

## Window

```text
collision = true
```

The renderer may use complex decorative meshes, but gameplay collision should remain predictable.

---

# 36. Pressure / Atmosphere

The structural boundary graph can also become the basis for atmosphere simulation.

Each edge should have:

```ts
sealed: boolean;
```

Examples:

```text
Hull wall        sealed
Window           sealed
Closed door      sealed
Open door        unsealed between rooms
Airlock closed   sealed
Hull breach      unsealed
Open bay         unsealed
```

This allows rooms to form pressure zones.

---

# 37. Destruction

This architecture also works well if Sidereal later supports damage.

A hull segment can transition:

```text
Intact Hull
    ↓
Damaged Hull
    ↓
Breach
```

while preserving the same logical edge.

Example:

```ts
edge.treatment = "vertical-hull";
edge.damageState = "breached";
edge.sealed = false;
```

The ship topology does not need to be reconstructed from scratch.

# 38. Validation

Validation should inspect the structural graph.

Recommended rules:

## Errors

```text
Exterior boundary has no valid treatment
Floor topology is invalid
Boundary edge self-intersects
Door references missing edge
Hull interface conflicts with another module
```

## Warnings

```text
Unsealed exterior edge
Room has no access
Room has no oxygen path
Engine has no supported mount
Hull segment has no armour
Disconnected floor island
```

The user should usually still be allowed to continue editing.

# 40. Structure Mode Visualisation

In Structure mode, avoid rendering huge opaque walls that obscure the floor.

Instead show the exterior boundary as:

- Strong edge line
- Small structural nodes
- Optional translucent wall preview
- Direction / exterior normal indicator
- Treatment icons

Example:

```text
○────○────○────○────○
      hull edge
```

Possible colours can distinguish:

```text
Exterior envelope
Interior partition
Opening
Unsealed edge
Selected edge
Validation issue
```

Exact colours should remain theme-configurable.

- Wall height
- Canopy slope
- Armour
- Engines
- Windows
- Exterior detail

Both views edit the same underlying topology.

# 42. Do Not Duplicate Structure Between Views

Avoid separate definitions such as:

```text

3D wall object
```

Instead:

```text
StructuralEdge
      ↓
2D representation
      ↓
3D generated mesh
```

The structural graph is authoritative.

Visual representations are derived.

# 45. Authoring vs Generated State

Separate authored data from generated data.

Example:

```ts
interface AuthoredStructuralEdge {
    treatmentOverride?: string;
    profileOverride?: string;
}
```

Generated state:

```ts
interface ResolvedStructuralEdge {
    kind: "exterior" | "partition";
    treatment: string;
    meshProfile: string;
    normal: Vec2;
    length: number;
}
```

This makes floor edits much safer.

If a floor polygon changes, regenerate the perimeter while attempting to preserve compatible authored overrides.

---

# 46. Preserving Overrides During Floor Changes

When the user changes the floor shape, generated exterior edges may change.

The editor should attempt to retain overrides based on:

- Same canonical endpoints
- Overlapping edge range
- Spatial proximity
- Same outward normal
- Previous segment ancestry

Example:

```text
User sets bow to CockpitGlass
        ↓
User extends bow by 1 m
        ↓
CockpitGlass assignment should ideally remain
```

Do not discard all custom hull treatments after every floor edit.

# 47. Recommended Terminology

To avoid confusion in both UI and code, use consistent terms.

## Floor

Walkable structural floor area.

## Structural Edge

A logical boundary between spaces or between the ship and exterior.

## Exterior Boundary

Structural edge with ship interior on only one side.

## Partition

Interior structural wall.

## Treatment

What occupies a structural edge.

## Opening

Door/window/hatch embedded into an edge.

## Hull Skin

Visible exterior geometry generated around the structural envelope.

## Armour

Additional exterior protection / decoration outside the hull skin.

## Interface

Structural attachment point for another module.

# 50. Main Design Rule

The most important rule for the implementation is:

> **Do not equate an exterior boundary with a wall mesh.**

Instead:

```text
Floor edge
    ↓
Structural boundary
    ↓
Boundary treatment
    ↓
Generated geometry
```

This allows the same underlying editor to represent:

- Flat walls
- Angled armour
- Cockpit windows
- Sloped noses
- Engine mounts
- Ramps
- Hangar doors
- Open bays
- Low hull sections
- Alien hulls
- Military armour
- Multi-deck transitions

without continually adding special cases.

# 52. Suggested Immediate Refactor of Current Designer

The current designer appears to generate tall wall meshes directly around the floor union.

Replace that pipeline:

```text
Floor
  ↓
Generated Wall Mesh
```

with:

```text
Floor
  ↓
Boundary Graph
  ↓
Default AUTO treatment
  ↓
Boundary Preview
  ↓
Generated Hull Geometry
```

In the editor:

- Exterior boundaries should primarily appear as editable lines.
- The full wall/hull geometry should be optional or translucent in Structure mode.
- Cockpit edges should be editable independently.
- Partitions should use the same edge topology.
- Validation should warn about unsealed boundaries instead of preventing them.

This should immediately improve the current floorplan workflow while leaving room for the more advanced hull system later.
