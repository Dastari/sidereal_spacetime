# Blender model migration

Status: Owner-approved direction; current Shipyard equipment installed
Last updated: 2026-09-08
Owners: Sidereal art and rendering

## Source of visual truth

The owner explicitly clarified: **“these are all being phased out in favor of blender models/meshs/materials etc...”**, referring to the current TypeScript voxel-solid models. This applies to current equipment and the model reconstruction work in the living art library.

**Blender is the source of truth for replacement visual assets:** editable `.blend` files, intentionally authored meshes, material assignments, UVs/textures where needed, rigs, animation and attachment nodes. Export validated glTF/GLB meshes and materials for Babylon. Preserve the authored silhouette, plate thickness, seams, bevels, curves and surface response through export.

The existing TypeScript `box(...)` solids and procedural voxel shape definitions are **legacy visual fixtures being retired**. Read them for current dimensions, origins, placement, semantic grouping and gameplay interfaces. Rebuilding their shapes in TypeScript, tweaking their palette, or merely exporting the same coarse voxel surface into a `.blend` file does not fulfil a model redesign. New modeling work takes place in Blender; deterministic Blender Python recipes are welcome when they retain editable authored geometry and materials.

Studless construction is an art direction, not a requirement that the visible replacement mesh be generated by a TypeScript voxel mesher. Do not quantize a replacement Blender surface back through the old mesher as the default visual export. Use native authored surface detail at the intended scale and validate actual runtime fidelity.

## Runtime and gameplay data

TypeScript still owns normal content definitions, runtime loading, assembly metadata, simulation and gameplay integration. Preserve stable design identity, placed-object UUIDs, installation transforms, footprint/collision contracts, interaction grants, inventories and state during migration. Changing a mesh grants no gameplay capability.

Existing sampled occupancy, material, collision and damage data may remain as separate gameplay/editing representations while their consumers are migrated. Derive a required proxy from the authored source, document its limitations and keep it separate from the visible mesh. Retiring TypeScript shape authoring does not itself implement or remove voxel damage, change authority rules, or authorize a database migration.

The current local damage preview can replace authored surfaces with a coarse sampled remesh. That behavior needs an explicit fidelity decision and validation during integration; it is not an acceptable reason to pre-degrade every undamaged replacement model. Record any unsupported damage/material path as a specific unresolved integration issue.

GLB material export must preserve the selected supported PBR inputs and baked textures. Validate glass/transmission in the actual selected export and Babylon path. The old opaque-only sampler's restrictions apply when that sampler is used; do not silently flatten the Blender material to fit it or claim unsupported optical/damage behavior is complete.

## Per-asset migration

1. Inventory the current runtime asset and all placements. Measure its bounds and trace the legacy generator, existing Blender files, renderer and gameplay consumers.
2. Select exact references and a precise canonical design in the [living art library](https://github.com/Dastari/sidereal_spacetime/blob/9c58c07774d7d3c4a58a40c49e90f2a2c647249c/assets/art-library/INDEX.md). Keep every original crop and previous revision.
3. Reconstruct the visual design as editable Blender source with real materials, appropriate topology, origin, sockets, footprint and crew clearance. Refine size and stat proposals separately from implemented gameplay.
4. Export the authored mesh/materials to a staged GLB. Produce any separately required occupancy/collision proxy without replacing the authored visible surface by default. Migrate the narrow loader/catalog adapter where necessary; do not continue the retired shape generator to avoid integration work.
5. Save actual Blender renders, transparent cutout, reference/previous/current comparisons and screenshots from the real Shipyard/client using that exact export. Validate scale, normals, material response, animation, draw/triangle/texture budgets and placement/draft compatibility. Keep failures and next actions in the ledger.
6. Request owner review for the exact revision. Integrate/publish only within the owner's authorization; final design approval and publication remain distinct. Retain the old source and ID mapping for reproducibility while retiring its generation path from the migrated asset.

## Current implementation boundary

The ten current Shipyard equipment assets now use nine explicitly approved native Blender designs across seventeen unchanged placements in both Shipyard and the game. The approved exports, sources, material emission and fixture descriptors are tracked in `assets/runtime/assembly/equipment-manifest.json`. Legacy equipment solids remain separate occupancy references; both exporters skip their visual batches. See [installation and validation](https://wiki.sidereal.dastari.net/Art/Library/Docs/shipyard-equipment/installation). Native equipment damage preview is explicitly unsupported; saved edits are retained and the UI reports this limitation instead of replacing approved art with a coarse remesh.

The six initial art-library construction experiments have preserved Blender sources and sampled visual exports. They predate this clarification and remain draft evidence, with fidelity problems recorded. Future revisions should preserve authored Blender meshes and materials as the visual deliverable. Keeping those historical experiments does not make their coarse visual export the new standard.

Start equipment work with [the reusable equipment prompt](https://wiki.sidereal.dastari.net/Art/Library/Docs/prompts/REDESIGN_CURRENT_EQUIPMENT) and [its current equipment queue](https://wiki.sidereal.dastari.net/Art/Library/Docs/CURRENT_EQUIPMENT). Follow [the ledger workflow](https://wiki.sidereal.dastari.net/Art/Library/Docs/WORKFLOW) for revision, feedback and owner sign-off. Existing voxel-study documentation describes the current implementation; this migration direction governs replacement art.


## Interim pilot hull publication

The owner authorized the first modular pilot-hull kit as an interim replacement while requesting a smaller, more tapered and swept-back cockpit. Revision r001 is installed through `assets/runtime/assembly/hull-manifest.json`: 34 native Blender hull placements, with retained equipment and thruster identities. Native hull roofs use the existing cutaway path. The old forward visual shell is retired at the module interface, while legacy gameplay proxies remain separate and unchanged. The installation is not final reference-fidelity approval; subsequent revisions remain under review. See [installation evidence](https://wiki.sidereal.dastari.net/Art/Library/Docs/shipyard-hull/installation-r001/README).
