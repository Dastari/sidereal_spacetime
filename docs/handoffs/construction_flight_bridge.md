# Qualified authored instance to playable ship bridge

Status: pure planner, private table declarations, typed ctx.db adapter, per-ship resolver and tests implemented; **not registered, not active flight authority**. Updated 2026-09-10. Cargo/seat/light release remains independent.

The current qualified native Wayfarer can be spawned, walked through and populated with independent cargo/interaction state. Its review entry temporarily sets `character.shipId` to the construction instance UUID, but that instance has no actual `ship`, station, shared motion or flight-fitting rows. A room document alone cannot grant piloting.

## Implemented first bridge

`packages/sim/src/construction-flight.ts` validates the persisted instance by reconstructing the exact source through its UUID map and the existing native walking qualifier. It accepts only source SHA256 `362f37217f63a44a470676f104c8368bd0973ca03f5e29eab190bc4d6df71340`, instance revision1, and existing one-deck qualified geometry. A copied hash with altered geometry/mapping fails. The server supplies a bounded, reserved system-local berth; the reducer request carries no transform.

The plan uses the existing **instance UUID as ship UUID** so deck, cargo, interaction and actor-location joins remain consistent. It allocates eleven fresh UUIDs: one pilot station, one flight computer and nine actuators. Each device maps its instance placed-object UUID back to the exact source definition. The station maps `equipment-control-seat` and `equipment-control-console`; the nine engine/thruster source IDs come directly from `LAB_FLIGHT_ACTUATORS`. Duplicate/reserved identities reject before writes. No existing ship, actor, admission, item, container or document is modified.

The complete plan includes a static ship row, a lean shared motion row with indexed cells and authoritative sample tick, station, computer, actuator bindings and flight definition. The initial station is **unoccupied and non-operational**; installing data is not a control grant. Activation remains a separate validated transition after the hooks below are implemented.

`packages/world/src/construction-flight.ts` supplies `installConstructionFlight(repository, request)` with exact instance revision and operation identity. The current live game/ownership/workspace `instance.spawn` access check precedes receipt replay. A new operation cannot install a second ship on the same instance. A retry returns the recorded IDs with no allocation/writes. The adapter reserves a safe berth, validates the full plan, then inserts all records/receipt synchronously. Storage errors propagate to the enclosing SpacetimeDB transaction; catching partial failures and continuing is forbidden.

## Physical provenance

The first bridge deliberately reuses `LAB_FLIGHT_MASS`, `LAB_FLIGHT_PROFILE`, `LAB_FLIGHT_SPEED`, `LAB_FLIGHT_COMPUTER`, all nine `LAB_FLIGHT_ACTUATORS`, `LAB_HULL` and compatibility `STARTER` scalars. These are the existing development installation values, **not** approved mass/payload/armor derived from art. Dynamic cargo/crew/fuel mass and routed power/fuel availability remain unimplemented.

Native GLB origins and physical force points differ. For example the port main drive visual is at (-3.625,-11.5625,.125), whereas its authored thrust application remains (-3.6,-14) with the existing height1.375. The bridge preserves the authored force point, rotation and thrust; it does not silently move forces to asset origins. Future socket qualification may revise those points through a new explicit physical definition.

The reused capsule is the current planar contact representation, not a claim that detailed new armor/cockpit geometry is destructible or matched by a mesh collider. Existing structural voxel/proxy authority remains separate. Ordinary interior entities still require health/damage definitions rather than voxel deformation.

## Required registration and activation integration

Private tables are declared in `construction-flight-tables.ts`; the actual typed database adapter is `construction-flight-authority.ts`. The per-ship resolver in `construction-flight-resolver.ts` admits exactly ten complete fitting rows, binds source IDs to fresh runtime IDs, applies installed/powered availability and fails closed on missing/corrupt/extra fittings, changed instance revision or flight-definition hash. The resolved fitting IDs have been exercised through the existing `stepSystemSpace`/IFCS solver: enabled authorized input accelerates, disabled input emits zero thrust and produces no idle motion change. These new modules are unregistered.

A content hash of the complete flight definition is stored at installation so source-code/content changes cannot silently retune an existing ship. The actual adapter preserves owner identity privately in its receipt table but projects only the minimal repeatable installation result. Global TypeScript check passed in `.runtime/construction-flight-tsc.log`.

1. **Register the implemented private additive binding/fitting tables.** A ship-to-instance binding stores exact source SHA, instance/deck/revision, flight-definition revision and dormant/active state. A station binding stores the fresh station ID, actual deck/seat/console placement IDs. Fittings store fresh runtime ID, ship ID, sourceDeviceId, placed-object ID, immutable definition and operational state. Index by ship; cap at the exact ten devices in this first definition. Preserve the same placed UUIDs and cargo rows. Do not reuse static source IDs as runtime fitting IDs.
2. **Register the implemented ctx.db adapter.** The repository is bound to `ship`, `shipWorldMotion`, `station`, private binding/fittings/receipt; the mandatory server berth hook must be connected to the existing canonical allocator. Reuse the shared-system bounded admission budget/clearance algorithm and canonical-system seed validation. Execute publication/spawn and flight installation as clearly distinct owner actions, with explicit additive operation receipts. Preserve old world-motion snapshots and do not run live refit implicitly.
3. **Wire the implemented shared tick resolver.** `stepSharedWorld` currently hardcodes the LAB mass/hull/device IDs for every ship. Replace that with a server-side resolver: legacy stock ships retain the existing definition; a bound construction ship requires its exact current active definition and complete fittings. Invalid/missing binding must fail closed, never fall back to a stock ship. Feed the existing `stepSystemSpace`/IFCS/contact solver; do not duplicate physics. Output telemetry must use the fresh actuator UUID while retaining the placed-object mapping for the renderer. Continue once-per-system stepping and idle no-op behavior.
4. **Native deck station authority.** `useStation` currently checks only laboratory XY range. Construction pilots require actual instance/deck, current owner/crew access, station operational state, qualified approach/seat support and LOS, unique occupancy, no conflicting couch/stair/traversal state and active input lease. The seat's own collider is handled by a separately qualified seat envelope, not globally removed. Loss/disconnect recovers to a supported approach and zeros IFCS input. Recheck station grant at input consumption. Ownership alone is never a pilot grant.
5. **Boarding/admission.** A flight installer must not teleport the actor or replace `worldAdmission` as a side effect. Explicit boarding/selection transitions must validate both source exit and destination entry, preserve the original ship and clear old station/input state. Replace the current review-return shortcut only through a defined playable location contract. Multi-account crew entry remains a separate permissioned path; an inventory grant cannot create it.
6. **Owner/remote presentation.** Owner clients consume the actual instance document/placement bindings and fresh station/device rows. Remote views map only the approved public exterior package, never private construction documents/interiors. TAB remains user choice. Read-only discovery must not cause an instance to become a ship or grant control.

## Native pilot next slice (unregistered)

`construction-pilot.ts` in sim qualifies the exact existing pilot seat collider and its source UUID map. The approved standing approach is (0,9.375), seated XY is the existing (0,10.25), and current supported elevation is .1875m. Normal walking retains the seat obstacle. A scoped seating transition excludes only its exact one native polygon and matching boundary edges; console, hull and all other obstacles remain. The full swept .3m body path must reach the seat. Exit searches eight bounded supported positions; other characters can block them.

`construction-pilot.ts` in world implements synchronous entry, command-consumption checks and recovery over a repository. `construction-pilot-authority.ts` binds that repository to actual private station/flight/location/grant rows, `constructionCollision`, native support and the existing `consumeInputControl` lease validator. User entry additionally requires that caller connection hold the lease; server command consumption validates the stored live owner lease. `construction-pilot-tables.ts` declares the occupied-seat reservation with unique station identity and a pending-recovery index. The table and reducer/tick hooks are unregistered.

Entry rechecks live game identity, exact accepted instance/deck, owner review permissions, operational active flight/computer, lease, station revision, standing/non-traversing pose, supported proximity and swept approach. It claims the station, records the private seat, updates accepted pose, clears prior input/aim and records an idempotent receipt. No ownership-only or click-only flight grant exists. Current command consumption rechecks exact occupancy/deck/revision/pose, current grants, active powered definition and current lease; a valid idle check writes nothing.

Disconnect/grant loss recovery does not require the capability that was lost. It clears motion input/aim and tries a supported, unoccupied exit. If all exits are blocked, the unique reservation remains pending, denies control and retries only through the pending index. Repeating the same blocked recovery produces no additional row writes. Invalid geometry is detected entirely before any writes and holds a pending reservation; errors from subsequent database mutations propagate normally to transaction rollback. A stale reservation cannot teleport an actor who has moved to another instance/deck.

Nine additional tests in `.runtime/construction-pilot-tests.log` cover actual native geometry, unmodified walking collision, entry/retry, wrong deck/revision/occupancy/permission/lease/support, current control checks, disconnect/grant-loss exit, blocked exit no-op retries, altered geometry, detached actor safety, and the **actual** input-control validator expiring a session and clearing stale motion. Full tsc passes. The ctx.db pilot wiring is typechecked; actual registered module/provider seating and recovery still require the next isolated authority proof. No pilot reducer, active-state transition, shared-physics call site, boarding/admission switch or client activation has been registered by this slice.
