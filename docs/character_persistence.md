# Character persistence and authentication boundary

## Implemented laboratory persistence

Inventory items, containers, liquids, hotbar references, hand/back equipment and balances remain private authoritative rows keyed by stable character/item/container UUIDs. Cosmetic preferences now also have a private `character_appearance` row. Previously the client held cosmetics only in React state, so appearance was lost on reload even though inventory persisted.

The `own_appearance` view projects only the authenticated owner's character ID, revision and canonical `appearanceJson`. Existing characters with no saved preference receive `{}` at revision0 without a read-side database write. `set_character_appearance` accepts the complete cosmetic document, expected revision and operation ID. Its 2 KiB input bound, explicit enum/color whitelist, revision compare-and-swap and128 retained receipts prevent malformed writes and duplicate application. An evicted operation cannot replay against a newer revision. Presets include all ten current looks and the legacy crew/explorer choices. Skin, hair and six material-color fields persist alongside supported body/armor/helmet/hair-style preferences. Equipment flags are rejected; appearance cannot grant or replace an equipped weapon/backpack.

The client must hydrate cosmetics from this projection and submit saves through the reducer. It must merge authoritative hand/back inventory separately at presentation time. The server has no historical appearance to recover from before this feature: previously unsaved React state cannot be reconstructed after it is gone.

## Multiple connections and distinct accounts

Private `connection_presence` rows distinguish up to16 active sockets for one admitted identity. Closing one tab leaves the character available to another tab. The final admitted game socket disconnect clears connected/sprinting state, station/couch occupancy, combat aim and movement commands. Same-account tabs deliberately share one character and station permission; they are not separate pilots. Commands remain serialized by their existing sequence/freshness rules. A non-final tab's command expires normally unless the remaining tab replaces it; no new exclusive socket control grant is claimed.

Two different identities still receive separate private laboratory ships and characters. These tests establish concurrent server authority, persistence and privacy, not shared-space multiplayer: there is no discovered-other-character projection, remote-player avatar renderer, crew invitation/boarding permission or shared fixture simulation in this slice. The one-character-per-identity lookup also remains a laboratory limitation.

Presence cleanup relies on the host's connection lifecycle callback. Graceful reconnect/restart evidence must not be represented as abrupt crash/fault-injection coverage; abnormal shutdown recovery remains a separate lifecycle gate.

## Authentication and explicit identity migration

Development transport reuses `sidereal.lab.token` from localStorage. Without it, the database creates a new development identity. Clearing browser storage or using another profile therefore selects a different identity; it does not delete the old inventory. The optional OIDC transport token is never written to that development key.

The owner superseded the Orchard issuer with the dedicated provider described in [ops/keycloak/README.md](../ops/keycloak/README.md). The compiled game policy permits exactly `https://auth.dastari.net/realms/dastari`, audience `sidereal-game`, a nonempty verified subject and a current bounded expiry. The explicit `hybrid-development` policy additionally permits this local server's exact `localhost`/`spacetimedb` issuer/audience. Production must deliberately switch to `oidc-only` after real-provider acceptance. Client email, display name, arbitrary issuers and dashboard-only tokens grant no game access.

The pinned SDK exchanges the original ID token for a WebSocket admission ticket with a 60-second expiry and no original-expiry claim. The server deliberately retains that expiry check. The client opens and subscribes a replacement connection every30seconds before closing the previous socket; OIDC token renewal follows the same overlap. This preserves a fresh authenticated presence lease without extending a ticket on client assertion. See [authentication.md](authentication.md) for the actual login and continuity evidence.

Admission checks run on connection and on every gameplay reducer; scheduled command consumption also checks a current admitted session. Private `auth_session` rows make views depend on admitted identity sessions, with expiry cleanup in the 50 ms world tick. Expired credentials reject actions immediately. A still-open expired socket can share the same principal's projection if another fresh game session exists; the view API cannot distinguish those sockets. Client renewal/logout must close the old socket, and strict per-socket read expiry also depends on host support. Views are principal-scoped and cannot inspect the requesting socket's JWT, so dashboard-only connections are rejected entirely rather than allowed to inherit another simultaneous game session's rows. This is not a general dashboard live-edit authorization implementation.

`request_identity_link(targetIdentity, expectedCharacterId, operationId)` requires an active development source and an already authenticated OIDC game target. `own_identity_links` exposes only requests in which the caller is source or target, including expiry and the expected character's name/UUID. The target calls `accept_identity_link(requestId, operationId)` within five minutes while both principals remain authenticated. The target must have no character/ship; existing-account merges are rejected for explicit review. The source must have exactly the reviewed character/ship and a bounded existing edit audit.

Acceptance atomically changes character/ship ownership and receipt ownership, retains every character/item/container/fitting/receipt UUID, stores an immutable source/target audit with the original receipt IDs, clears movement/helm/couch/aim, and retires the old development identity. Character-keyed inventory, appearance, equipment, hotbars and balances are not rewritten or regranted. Retried acceptance is idempotent; conflicting operations fail. Retired tokens cannot reconnect, seed a replacement character or write through an already open socket. Old rename receipt IDs remain valid for safe retry under the new owner. No email matching or browser-provided owner transform is involved.

The PKCE login/callback/renewal/logout interface and HTTPS application origins are a separate integration. Real-provider token acceptance and the optional complete migration smoke remain explicit gates; passing development-token tests is not production login proof. Logout closes the client socket; provider logout alone cannot invalidate an already issued bearer token before its expiry without an additional revocation integration. Same-account sockets deliberately share character authority; global input sequences may supersede an older tab and do not constitute an exclusive per-tab control protocol.
